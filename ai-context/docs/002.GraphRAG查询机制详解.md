# GraphRAG 查询机制详解

> 详解 GraphRAG 三种搜索模式（Global / Local / DRIFT）的完整数据流：从用户查询到最终回答。
>
> 源码路径：`packages/graphrag/graphrag/query/structured_search/`
>
> 配合 [001.GraphRAG数据模型与存储.md](./001.GraphRAG数据模型与存储.md) 阅读。

---

## 1. 三种搜索模式概览

| | Global Search | Local Search | DRIFT Search |
|--|--------------|-------------|-------------|
| **适用问题** | 宏观、全局概括 | 具体实体/细节 | 从宏观到细节逐步深入 |
| **核心数据** | 社区摘要报告 | 实体+关系+文本块 | 社区报告 → 实体+关系 |
| **向量检索** | 不用（直接读报告） | ✅ 实体描述向量 | ✅ 实体描述向量 |
| **LLM 调用** | Map(N次) + Reduce(1次) | 1 次 | 多次（迭代） |
| **Token 预算分配** | 全给报告 | 社区25% + 图结构25% + 文本50% | 动态分配 |

## 2. Global Search（全局搜索）

### 2.1 适用场景

```
"这个数据集讲了什么？"
"主要有哪些主题？"
"整体概况是什么？"
```

### 2.2 核心思路

不做向量检索，直接读取指定层级的**所有社区摘要报告**，并行让 LLM 从每份报告中提取关键要点（Map），再汇总为最终答案（Reduce）。

### 2.3 完整数据流

源码：`global_search/search.py` + `global_search/community_context.py`

### 2.4 源码关键路径

```python
# global_search/search.py:142-214
async def search(self, query, conversation_history=None):
    # Step 1: 构建上下文（分 batch）
    context_result = await self.context_builder.build_context(query=query, ...)
    
    # Step 2: Map（并行）
    map_responses = await asyncio.gather(*[
        self._map_response_single_batch(context_data=data, query=query, ...)
        for data in context_result.context_chunks  # 每个 chunk 是一个 batch
    ])
    
    # Step 3: Reduce
    reduce_response = await self._reduce_response(
        map_responses=map_responses, query=query, ...
    )
    return GlobalSearchResult(response=reduce_response.response, ...)
```

## 3. Local Search（局部搜索）

### 3.1 适用场景

```
"战斗系统的伤害计算公式是什么？"
"EventBus 是怎么工作的？"
"背包系统和商城系统有什么关系？"
```

### 3.2 核心思路

将用户查询 embedding → 向量库检索最相似的实体 → 沿图结构展开获取关系、社区报告、原始文本 → 拼接为上下文 → LLM 生成回答。

### 3.3 完整数据流

源码：`local_search/search.py` + `local_search/mixed_context.py`

### 3.4 上下文混合比例

```python
# factory.py:84-96
context_builder_params = {
    "text_unit_prop": 0.5,      # 50% 给原始文本
    "community_prop": 0.25,     # 25% 给社区报告
    # 剩余 25% 给图结构（实体+关系+协变量）
    "top_k_mapped_entities": 10,      # 最多匹配 10 个实体
    "top_k_relationships": 10,        # 每个实体最多 10 条关系
    "max_context_tokens": 8000,       # 总 token 预算
}
```

### 3.5 关系过滤与排序策略

源码：`context_builder/local_context.py:232-317`

```
对每个匹配到的实体，获取其所有关系：

1. in-network 关系（优先）:
   匹配实体之间互相连接的关系
   → 这些是最相关的（用户问的就是这些实体之间的关系）

2. out-network 关系:
   匹配实体与未匹配实体之间的关系
   → 按 "共享邻居数" 排序（mutual links 优先）
   → 再按 rank/weight 排序

3. 截断:
   总关系数 ≤ top_k_relationships × 匹配实体数
   例如：10 × 3 = 最多 30 条关系
```

## 4. DRIFT Search（漂移搜索）

### 4.1 适用场景

```
"战斗系统的整体设计理念是什么？具体有哪些子模块？各自如何配合？"
（从宏观到微观的递进式问题）
```

### 4.2 核心思路

结合 Global 和 Local 的优点：先从社区报告出发获取宏观理解（Primer），然后通过 Local Search 逐步深入具体问题（Follow-up），沿着社区层级树构建问答链。

### 4.3 简化数据流

```
用户查询："战斗系统的设计理念和实现细节？"
                    │
                    ▼
    ┌────── Primer 阶段（类似 Global）──────┐
    │  读取社区报告，找到最相关的社区          │
    │  生成初始的宏观回答                     │
    │  生成 follow-up 子问题列表             │
    └──────────────┬───────────────────────┘
                   │
         ┌─────────┼─────────┐
         ▼         ▼         ▼
    ┌─ Follow-up 1 ─┐ ┌─ Follow-up 2 ─┐ ...
    │ "伤害计算的    │ │ "Buff系统如何  │
    │  公式是什么？" │ │  与技能联动？" │
    │ (Local Search) │ │ (Local Search) │
    └───────┬───────┘ └───────┬───────┘
            │                 │
            └────────┬────────┘
                     ▼
              Reduce: 合并所有答案
                     │
                     ▼
               最终综合回答
```

## 6. 与 LightRAG 查询的对比

### 6.1 宏观查询对比

```
问题："这个数据集的整体概况是什么？"

GraphRAG Global Search:
  1. 读取所有社区摘要报告
  2. Map: 对每份报告提取要点（并行 N 次 LLM）
  3. Reduce: 合成最终答案（1 次 LLM）
  总 LLM 调用: N+1 次
  优势: 确保覆盖所有主题（每个社区都被处理）

LightRAG Global Mode:
  1. LLM 提取高层关键词
  2. embed(关键词) → relationships_vdb 向量检索
  3. 获取 top-k 关系 + 关联实体 + 文本
  4. LLM 生成回答
  总 LLM 调用: 2 次（关键词提取 + 回答生成）
  优势: 快、便宜；缺点: 可能遗漏与关键词不相似的主题
```

### 6.2 局部查询对比

```
问题："战斗系统是如何工作的？"

GraphRAG Local Search:
  1. embed(query) → 向量库找实体
  2. 图遍历获取关系
  3. 加载社区报告 + 原始文本
  4. LLM 生成回答
  优势: 上下文更丰富（社区摘要提供宏观背景）

LightRAG Local Mode:
  1. LLM 提取低层关键词
  2. embed(关键词) → entities_vdb 向量检索
  3. 图遍历获取关系
  4. LLM 生成回答
  优势: 多了一步关键词提取，检索更精准
```

### 6.3 核心差异

| 维度 | GraphRAG | LightRAG |
|------|----------|----------|
| **宏观查询入口** | 社区摘要报告（预计算） | 关系向量检索（实时） |
| **需要关键词提取？** | 不需要 | ✅ LLM 提取双层关键词 |
| **向量检索对象** | Entity description | Entity content + Relationship content |
| **关系获取** | 图遍历 | 向量检索 + 图遍历 |
| **上下文组成** | 社区报告 + 实体 + 关系 + 文本 | 实体 + 关系 + 文本 |
| **Global 成本** | N+1 次 LLM（每个社区报告一次 Map） | 2 次 LLM |
| **Global 覆盖度** | ✅ 全覆盖（遍历所有报告） | 可能遗漏（依赖向量匹配） |

## 7. 常见疑问

### Q: Global Search 为什么不用向量检索找社区报告？

因为 Global Search 的目标是**全局概括**——需要覆盖所有社区，不能漏掉任何主题。向量检索只返回语义最相似的 top-k，可能遗漏与查询措辞不同但同样重要的社区。所以直接读取全部报告，用 Map-Reduce 保证完整覆盖。

### Q: Local Search 的向量库里存的是什么？

Entity 的 **description embedding**。查询时将用户查询 embed 后做 cosine similarity 找到最相关的实体，然后从实体出发沿图结构展开。

GraphRAG 不在向量库中存关系（不像 LightRAG 有 relationships_vdb），关系通过图遍历获取。

### Q: 为什么 Local Search 要分三部分上下文？

这是 GraphRAG 的**混合上下文**策略（Mixed Context）：
- **社区报告 (25%)**：提供宏观背景（"这些实体属于什么领域"）
- **图结构 (25%)**：提供精确的实体描述和关系描述
- **原始文本 (50%)**：提供细节和原始表述

三者互补：报告给方向，图结构给结构，文本给细节。

### Q: Map 阶段的并行度有限制吗？

默认 `concurrent_coroutines = 32`，即最多 32 个 Map 请求并行。如果社区报告分成 50 个 batch，会分多轮执行。

### Q: 为什么 Global Search 的 Map 阶段要求 JSON 输出？

源码中 Map 阶段要求 LLM 输出 JSON 格式的关键要点列表（包含 description 和 score），这样 Reduce 阶段可以按 score 排序、按 token 截断，实现结构化的信息融合。Reduce 阶段则不要求 JSON，直接生成自然语言回答。

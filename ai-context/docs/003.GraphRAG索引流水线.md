# GraphRAG 索引流水线

> 详解 GraphRAG 从原始文档到可查询数据的完整处理流程。每一步做了什么、谁执行、成本如何。
>
> 配合 [001.GraphRAG数据模型与存储.md](./001.GraphRAG数据模型与存储.md) 阅读。

---

## 1. 流水线总览

```
原始文档 (.txt / .csv / .pdf)
    │
    ▼ ① 文本分块 (程序)
TextUnit 列表
    │
    ▼ ② 实体/关系抽取 (LLM)
Entity + Relationship 列表
    │
    ▼ ③ 合并去重 (程序)
知识图谱 (NetworkX)
    │
    ▼ ④ Leiden 社区检测 (算法)
Community 层级树
    │
    ▼ ⑤ 社区摘要生成 (LLM)
CommunityReport 列表
    │
    ▼ ⑥ Embedding 生成 (Embedding 模型)
向量存入向量库
    │
    ▼ ⑦ 输出 Parquet 文件
output/ 目录下的 .parquet 文件
```

---

## 2. 各步骤详解

### ① 文本分块

| | 详情 |
|--|------|
| **执行者** | 程序 |
| **LLM 成本** | 零 |
| **输入** | 原始文档 |
| **输出** | TextUnit 列表 |

```python
# workflows/create_base_text_units.py:99-111
async for doc in documents_table:
    chunks = chunk_document(doc, chunker, prepend_metadata)
    for chunk_text in chunks:
        row = {
            "id": gen_sha512_hash({"text": chunk_text}, ["text"]),
            "document_id": doc["id"],
            "text": chunk_text,
            "n_tokens": len(tokenizer.encode(chunk_text)),
        }
        await text_units_table.write(row)
```

**分块策略**：
- 默认按 token 数切分（~300 token/块）
- 可选 `prepend_metadata`：在每块文本前加入文档标题、创建时间等元数据
- 每块 ID = `sha512(text)` → 相同文本不会重复

---

### ② 实体/关系抽取

| | 详情 |
|--|------|
| **执行者** | LLM |
| **成本** | **主要成本之一**（每个 TextUnit 至少 1 次 LLM 调用） |
| **输入** | 每个 TextUnit 的文本 |
| **输出** | Entity + Relationship 列表 |

**LLM Prompt 要求**：给定一段文本和预定义的实体类型列表（如 PERSON, ORG, CONCEPT），抽取所有实体和它们之间的关系。

```
提取结果示例（一个 TextUnit）：

Entities:
  ("战斗系统", "SYSTEM", "游戏核心玩法，负责伤害计算和战斗流程")
  ("技能", "MECHANIC", "玩家释放的攻击手段")
  ("伤害计算", "MODULE", "基于攻击力和防御力的伤害公式")

Relationships:
  ("战斗系统" → "技能", "玩家通过释放技能发起战斗")
  ("战斗系统" → "伤害计算", "战斗系统依赖伤害计算")
```

**Gleaning**（二次提取）：可选配置 `max_gleanings`，让 LLM 检查是否遗漏了实体/关系，增加召回率但增加成本。

---

### ③ 合并去重

| | 详情 |
|--|------|
| **执行者** | 程序 |
| **LLM 成本** | 零（或少量，用于描述融合） |
| **输入** | 所有 TextUnit 的抽取结果 |
| **输出** | 去重后的知识图谱 |

**合并规则**：

```
同名实体合并：
  - 保留类型（取最常出现的）
  - 多条 description → LLM 融合为一段统一摘要
  - text_unit_ids = 所有出现过的 TextUnit ID 的并集

同源-目标关系合并：
  - weight += 1（每出现一次累加）
  - 多条 description → LLM 融合
  - text_unit_ids = 所有出现过的 TextUnit ID 的并集
```

**构建图**：

```python
# 构建 NetworkX 图
G = nx.Graph()
for entity in entities:
    G.add_node(entity.title, ...)
for rel in relationships:
    G.add_edge(rel.source, rel.target, weight=rel.weight, ...)

# 计算实体 rank（度数）
for node in G.nodes():
    entity.rank = G.degree(node)
```

### ④ Leiden 社区检测

| | 详情 |
|--|------|
| **执行者** | 纯算法（`graspologic-native` Rust 实现） |
| **LLM 成本** | 零（毫秒级完成） |
| **输入** | 知识图谱（节点+带权边） |
| **输出** | 社区层级树 |

**层级 Leiden（hierarchical_leiden）**：

```
参数: max_cluster_size（默认 10）

过程:
  1. 对整图运行标准 Leiden → 得到初始社区划分
  2. 检查每个社区的大小
  3. 如果社区大小 > max_cluster_size:
     - 提取该社区的子图
     - 对子图再次运行 Leiden（递归）
     - 原社区成为父节点，子社区成为叶子
  4. 重复直到所有社区 ≤ max_cluster_size

输出:
  Level 0: 叶子社区（最细粒度）
  Level 1: 中间层
  Level N: 根社区（最粗粒度）
```

**反向填充**：每个社区记录其包含的 entity_ids、relationship_ids、text_unit_ids。

---

### ⑤ 社区摘要生成

| | 详情 |
|--|------|
| **执行者** | LLM |
| **成本** | **主要成本之一**（每个社区 1 次 LLM 调用） |
| **输入** | 社区内的实体、关系、可选原始文本 |
| **输出** | CommunityReport |

**生成顺序**：自底向上（先叶子后父节点）

```
Level 0（叶子社区）:
  输入 = 社区内的 entities + relationships 描述
  → LLM 生成摘要报告

Level 1（父社区）:
  输入 = 子社区的摘要报告 + 社区内的 entities + relationships
  → LLM 生成更高层的摘要报告
```

**报告结构**：

```markdown
# {社区标题}

## Summary
{概述}

## Key Entities
- {实体1}: {角色描述}
- {实体2}: {角色描述}

## Findings
1. {发现1} [Data: Entities (id1, id2); Relationships (id3)]
2. {发现2} [Data: Entities (id4)]

## Rating
{重要性评分}/10
{评分理由}
```

---

### ⑥ Embedding 生成

| | 详情 |
|--|------|
| **执行者** | Embedding 模型 |
| **成本** | 低（批量调用 Embedding API） |
| **输入** | Entity description / CommunityReport full_content |
| **输出** | 向量，存入向量库 |

**被 embed 的内容**：

| 数据 | 被 embed 的字段 | 用途 |
|------|----------------|------|
| Entity | `description` | Local Search / DRIFT 的实体语义匹配 |
| CommunityReport | `full_content` | DRIFT Search 的初始匹配 |

---

### ⑦ 输出

所有数据以 Parquet 格式写入 `output/` 目录，向量存入配置的向量库（默认 LanceDB）。

## 3. 成本汇总

| 步骤 | 执行者 | 调用次数 | 成本级别 |
|------|--------|---------|---------|
| 文本分块 | 程序 | — | 零 |
| 实体/关系抽取 | LLM | O(TextUnit 数) | **高** |
| 描述融合 | LLM | O(重复实体数) | 中 |
| Leiden 聚类 | Rust 算法 | 1 | 零 |
| 社区摘要 | LLM | O(社区数 × 层级数) | **高** |
| Embedding | Embedding 模型 | O(实体数 + 社区数) | 低 |
| 总计 | | | 主要来自 LLM 抽取 + 摘要 |

**实际数据参考**（微软论文中的数据）：

```
一本书 (~100K token):
  ~300 个 TextUnit
  ~300 次 LLM 抽取调用
  ~50 个社区
  ~50 次 LLM 摘要调用
  总计 ~350 次 LLM 调用
```

## 4. 配置要点

```yaml
# settings.yaml 中的关键索引配置

chunks:
  size: 300          # 每块 token 数
  overlap: 100       # 块间重叠 token

extract_graph:
  completion_model_id: extraction_model    # 抽取用的 LLM
  entity_types: [organization, person, geo, event]  # 预定义实体类型
  max_gleanings: 1   # 二次提取次数（0=不做）

community_reports:
  completion_model_id: extraction_model    # 摘要用的 LLM
  max_input_length: 8000  # 社区上下文的 token 上限

cluster_graph:
  max_cluster_size: 10    # Leiden 最大社区大小
  use_lcc: true           # 只保留最大连通分量
  seed: 0xDEADBEEF        # 随机种子（可复现）
```

## 5. 与 LightRAG 索引流程对比

| 步骤 | GraphRAG | LightRAG |
|------|----------|----------|
| **文本分块** | ✅ 按 token | ✅ 按 token |
| **实体/关系抽取** | ✅ LLM | ✅ LLM |
| **关系 keywords** | ❌ 不生成 | ✅ LLM 生成 relationship_keywords |
| **合并去重** | ✅ 同名合并 + 描述融合 | ✅ 同名合并 + 描述融合 |
| **图存储** | NetworkX（内存） | 图数据库（Neo4j/NetworkX） |
| **社区检测** | ✅ Leiden 层级聚类 | ❌ 无社区 |
| **社区摘要** | ✅ LLM 生成 | ❌ 无 |
| **Entity Embedding** | ✅ description | ✅ entity_name + description |
| **Relationship Embedding** | ❌ 可选（不用于检索） | ✅ keywords + entities + description |
| **向量库** | LanceDB（Entity 向量） | Nano-VectorDB / Milvus（Entity + Relationship） |
| **输出格式** | Parquet 文件 | 图数据库 + 向量库 |
| **额外索引成本** | Leiden（零）+ 社区摘要（LLM） | 关系 keywords（LLM）+ 关系 Embedding |
